# 真实混合研究与状态写入冲突修复

本阶段以 `37519c4b` 为真实运行源码，进行一个有上限的混合案例。**初始规划和基准后的模型选点已实际发生，但研究失败，整体未完成。** 共2次 Token Rhythm 请求、11,344 tokens、1个原生基准／7个模块。失败后没有付费重试或新原生场景，也没有续跑旧任务。

## 真实执行到了哪里

任务 `20260927_192816_356d6a` 的首组研究七东线停车治理；第二组 `20260927_192816_7ece20` 原计划研究长江村路停车＋单向，尚未开始。初始提议一次通过，用量4,876 tokens，两个组各有独立新基准，总上限6个场景、6次模型请求。

第一组完成新的TranStar基准后，模型读取实际速度、V/C和区域范围，选择七东线 `3244→3245` 与 `3245→3244` 两向停车由3级改为1级。此次选点用量6,468 tokens。随后，写入已校验的模型决策时，Windows 对 `dispatches/<任务>.json.tmp → <任务>.json` 的替换返回 `WinError 5`。程序因此停止，**治理动作没有执行**，第二组也没有启动。

这次失败发生在本机状态文件发布处，不能称为TranStar求解失败。原始错误、已接受但未执行的模型选择、首次新基准和所有未完成项均保留。页面显示“运行失败”，地图只展示已完成基准，明确尚无治理结果。

[局部证据核对](validation/20260927_mixed_routing_partial_check.json)重新读取了原生输入、输出、7个模块日志与时间戳，重算基准指标，并核对模型收到的观测及摘要哈希与此基准一致；没有为失败任务出具完整研究证书。

## 已实现与离线验证

用普通 Windows 文件读句柄占用临时测试文件，已复现相同 `WinError 5`。这证明现有单次替换可能被并发读取阻止；原始运行未记录阻塞句柄的归属，不能指认具体是哪一个读取方。

[save_json](../traffic_agent/data.py) 改为先序列化完整内容，使用独立临时文件并刷新到磁盘，再原子替换。仅对Windows的访问／共享／锁冲突做最多9次本地替换尝试，累计退避等待1.63秒。只重试文件替换，不重新计算值、不重复模型或原生调用。无法恢复时仍抛出错误并保留旧记录；不会通过直接截断目标文件来掩盖问题，也不清理其他写入者或旧故障留下的临时文件。

新增5项持久化检查和1项真实控制器联调：

- 实际Windows读句柄释放后，同一完整快照可成功发布。
- 读句柄持续占用时达到有限重试上限，旧文件字节保持不变。
- 非共享类IO错误不重试，非法JSON不触碰旧记录。
- 两个并发写入者使用不同临时文件，最终文件始终是其中一个完整快照。
- 在合成控制流程中，于模型选择已返回、状态尚未发布的位置持有真实Windows读句柄；遇到相同错误后完成整套控制流程，仍恰好6次合成模型请求、6个合成场景，无重复调用。

**400项Python检查通过**，见[日志](validation/20260927_state_persistence_tests.log)。前端源码未改变；浏览器只读核对真实失败、未完成项与基准地图。本阶段的故障注入、回归检查不使用密钥或付费服务。通用失败提示改为“研究执行中断”，避免把存储异常直接归因于TranStar。
