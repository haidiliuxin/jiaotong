# 单向道路组织：真实路权配对验证

后续进展：随包Vehicle1分车型流程已在另一组新配对中通过实际禁行响应，见[单向分配适配](单向分配适配.md)。本文保留默认分配程序的原负例，两种配置不能混作政策收益对照。

草案S2允许局部禁转或单向组织。本次另建单向组织工具，不把单个禁转等同整条方向禁行。试验 `20260908_060332_oneway` 完成两场景、14次模块调用，记录通过独立核验，但**机动车禁行没有实际生效，普通oneway执行入口仍关闭**。

## 措施和预选规则

依据手册附录1-42，将`ManageR1.txt`一条有向路段的小汽车、摩托车、货车、常规公交四列由允许码0改为路段管理禁行码2；出租车按小汽车路权并另查出租车输出。反向保持四类通行码0，其他路权、车道、几何及全部OD不变。本阶段只允许一条方向，不宣称多路段单向网络或反向增车道。

选点采用已完成主实验的未治理基准，确认其输入与原案例相同；在2/3类道路、停车3/4、长0.1–1.5km、q≥500、1<VC≤4、速度<40的503项候选中，按qL/v排序，最多检查200项并取首个合格项。第23项红景路 **5991→5990** 通过，反向5990→5991保留。规则、排除原因、边界路径均在新仿真前写入`selection.json`，不按治理后收益挑选。

图检查覆盖654条既有公交线路的所有有向边，包括只含两个节点的线路和首尾段。小汽车（含出租车）、摩托车、货车分别建立通行图，保留已有禁转，不借虚拟连接线绕行；对关闭方向原可用的进入/离开状态以及端点OD接入逐项检查。此方向三类图各3组检查均通过，最大额外绕行0.283km、最大长度比1.428788，低于2km和3倍上限。端点路径示例为5991→4776→4775→5990。图证明仅针对已编码网络，不证明实际标志条件或模型正确执行了全部已有禁转。

## 将问题定位到阻抗与分配的连接

手册附录2-40把`ManageR1.dat`描述为0/1缓存，但此V4.8程序实际逐行保留输入的0/1/2代码。新基准已经含93个码2字段，单向后97个；两场景全部32,981行均与相应输入的八类通行码精确相同。核验已按观察到的版本行为改为精确比较，不接受任意非零值替代。

首次运行记录仍保留原来的二值缓存假设及`cache_matches_all_access_rows=false`；`verification.json`同时保存原判断与复核后的精确码判断。只修正缓存解释，原始场景、运行记录和流量没有改写；实际禁行结果仍为false。

进一步只读检查发现，五个`Ljt_car/taxi/motor/truck/bus.dat`均在本次运行期间新生成，且只在目标FT路段发生变化：**474.67→9,999,999,999**。路段管理已进入车型分配阻抗，但最终流量未响应。因此下一步应追踪车型阻抗的实际消费路径，不能将问题简单归结为禁行码2未进入缓存，也没有依据盲目改成默认禁行码1。

上述证据不证明内部实现根因；仅将排查范围从输入写入推进到车型阻抗与最终分配之间。详见[阻抗审计](../智能体实验/probes/20260908_060332_oneway/impedance_audit.json)。单向组织与ManageN禁转是两条不同措施链，不能据此声称此前禁转问题已修复。
