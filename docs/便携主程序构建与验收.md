# 便携主程序构建与验收

> 2026-09-27：新增自然语言智能规划候选包、独立空凭据检查和整个任务核验器，最新构建状态见[智能规划便携候选验收](20260927智能规划便携候选验收.md)。下面的规则任务原生验收仍只证明相应规则流程，不能计为大模型闭环通过。最新版真实规划和另一台物理电脑实跑仍待验证。

目的：提供可以完整解压后启动的主程序，把Python、编译器、原生程序、案例及地图放在同一目录，降低对评审机器开发环境的依赖。主程序包包括普通智能体CLI、网页停车流程，以及显式禁转和单向适配的运行依赖。研究批处理和正式PDF出版工具继续从完整仓库使用。

## 隔离与完整性

保留本机已经用于验证的Python 3.12解释器和标准库；排除第三方site-packages与开发测试缓存。`python312._pth`列出包内相对路径，以隔离模式加载包内site启动钩子，用户site关闭，不从系统Python、用户目录或PYTHONPATH取得依赖。路径隔离机制依据[Python官方Windows打包说明](https://docs.python.org/3.12/using/windows.html#finding-modules)。

标准库和启动钩子放在`python312.zip`内，避免启动钩子自身产生缓存。钩子设置`sys.dont_write_bytecode=True`，对原生包装器直接启动、未传`-B`的子解释器同样生效。启动检查同时验证路径隔离、用户site和缓存策略；验收还需单独运行不带`-B`的子解释器，再检查包内容未变化。

本机实际探针发现Python 3.12.6的`._pth`在启用`import site`后，仅有isolated标志仍会加入用户site。因此包内同时提供不含绝对home路径的`pyvenv.cfg`，使用`include-system-site-packages = false`在用户site处理前关闭它。必须以实际子解释器的sys.path和ENABLE_USER_SITE检查为准，不能只看到isolated=1就宣布隔离成功。

MinGW按完整目录复制，保留许可证。原生运行文件和案例逐字节复制，不通过删减未知缓存或DLL来压缩体积。每个不可变文件记录大小与SHA256；缺失、额外文件、同大小篡改、LFS指针、越界路径与大小写冲突都会阻止启动。只允许“智能体实验”作为可写输出区。

本机移动目录验收还发现：复制后的MinGW位于中文路径时，能回答版本和目标架构，但实际链接包装器退出116。原编译器对同一源码和工作目录可正常编译；仅创建英文目录联接仍不足，因为GCC会还原实际安装路径。启动器因此为包内编译器创建临时英文目录联接，并经`portable-tools/gcc.exe`增加`-no-canonical-prefixes`。所有原编译参数和包装器源码保持不变。代理保留返回码，并用Windows作业对象管理子编译进程，避免超时后留下编译子进程。

英文映射只对当前启动及子进程有效，正常退出后非递归移除自己创建的联接，保留编译器目标目录。如果临时目录的路径和短名称均包含非英文字符，则明确报错，要求解压到纯英文目录；不偷偷调用系统其他gcc。环境检查必须继续做一次实际编译，不能用“找到gcc”替代。

`launch.cmd`调用本包Python。`traffic_agent.portable`先核对清单，再记录实际解释器、sys.path、隔离状态与来源提交，然后进入既有启动器。编译器PATH仅对本次进程及子进程生效。不会修改系统Python、代理、环境变量或软件授权。

文件摘要证明传输一致性，不是数字签名；环境检查不代表模型授权、原生响应或真实求解通过。

## 构建

先提交运行源码，再建立不存在的新目录：

```powershell
.venv/Scripts/python.exe scripts/build_portable.py 工作材料/便携构建/20260922主程序 --compiler-root C:/mingw64
```

构建器保存来源提交、Python版本、编译器目标与版本、原生程序和案例摘要。输出完整目录及同名ZIP。构建目录和验收解压目录均忽略Git；最终验收后再把ZIP与对应清单、验收记录放入成果目录。

## 验收层次

1. 把ZIP解压到另一个含空格及中文的新目录，确认文件摘要完全一致。
2. 在子进程中将PATH限制到Windows系统目录，并给PYTHONHOME/PYTHONPATH设置不存在的干扰值；使用包内Python进行隔离检查和主程序启动检查。不得修改用户全局变量。
3. 使用包内MinGW核对目标并编译所用包装器，证明不依赖开发机的gcc路径。显式禁转与单向依赖分别检查。
4. 从新目录运行默认四场景停车验收，用包内核验器重读输入和结果、检查四数组基准复跑并封存。原生研究正在执行时先等待它结束，避免多个实验相互占用机器资源。
5. 核对网页启动、任务记录、实际地图与报告，并检查源案例摘要未改变。关闭本次检查创建的服务时只操作已确认的进程。
6. 记录本次到底验证了哪些流程。新的停车求解不能代替新环境下的完整禁转/单向响应，也不能把同机解压验收写成另一台电脑重跑。

最终发布需包含：ZIP摘要、内部清单摘要、源码提交、解释器与编译器版本、测试日志、新JOB编号、原生调用数及独立核验结果。尚未完成的步骤明确保留待验收状态。

`scripts/validate_portable_environment.py <ZIP> <新的中文解压目录> <新的证据目录>`自动完成前三层检查。用户site注入探针先在普通解释器下执行正对照，再要求包内解释器拒绝它；最后重核全部不可变文件。它不调用交通模型，报告必须标明`new_model_calls=0`。旧草稿及失败记录保留，只有新构建包的验收通过后才能发布。

网页已经完成四场景后，可用`scripts/archive_existing_portable_run.py <解压目录> <任务编号> <environment_verification.json> <证据目录>`做一次严格核验和封存。它要求对应环境记录、任务已完成且尚未封存，调用包内核验器，前后检查不可变文件；新增模型调用为0，另外记录已观察到的28次调用。未完成、错配清单和已封存任务会拒绝处理，不能用该命令重跑模型。已封存任务继续用原`verify_experiment.py --archive`复核。

已有三策略挑战正在运行时，可用`scripts/accept_portable_runtime.py <解压目录> <通过的environment_verification.json> <前序挑战目录> <新的真实验收证据目录>`串接单次验收。它先核对环境记录与运行包清单，等待指定挑战完成并通过核验封存，然后只启动一次默认停车四场景、独立核验并封存。输出记录保留进程号、真实任务ID、28次调用和源案例不变检查。等待或观察超时不重启、不终止原任务，也不产生通过结论；运行未完成时调用数记为未知。已有证据目录会拒绝覆盖。
