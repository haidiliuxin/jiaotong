# TranStar新增禁转未响应：可复现问题材料

本文是仓库内的问题说明，未向任何外部人员发送。用于后续定位或在获得授权后与软件维护方沟通。

## 环境和预期

Windows，赛事提供的TranStar城市交通版V4.8试用版及南京调整案例。采用Mparam631中多路径增量加载5轮。固定需求、路网、公交线路与停车设置，只对一个ManageN禁转三元组做变化。预期新增禁转能够改变相应合法路径选择，并在可信的转向输出中不再出现该转向流量。

执行链：M3DataRoadNetwork → M3DataBusNetwork → M3DataTrafficManage → M6AssignVehicle → M6TrafficLoadLinkVeh → M6TrafficLoadNodeVeh → M6NodeQueueDelay。各模块工作目录为隔离运行环境的programs，场景路径通过files/runinfo_vc6.txt提供。

## 已有最小政策差异

| 条件 | 对照和观察 |
| --- | --- |
| 红景路新增4797→5990→5991 | 原663条变664条，ManageNM集合匹配；小汽车转向表1019.9不变，四类路段数组不变 |
| 改为最短路增量5轮，派生参数统一700 | 使用新的匹配基准；转向量1090.61不变，未恢复新增禁转响应 |
| 补齐原软件空tmp目录后重跑 | 多路径匹配基准与禁转仍为1019.9，目录差异不是已证实原因 |
| 新进口6669→4994增加禁转4995 | 该进口原来没有禁转规则；转向量2009.1不变，四类数组相同 |
| 移除全部663条规则的控制实验 | 24,082条路段流量、11,715条速度变化，不能认为软件整体不读取ManageN |
| 全新节点4825新增5020→4825→5058 | 20,356条路段流量、6,953条速度变化；目标转向表由0变25.62，仍不能验证禁转正确生效 |

原规则前28条均有有效GEOM边，但其中15条在转向表中为正；因此“遇到第一条无效规则便停止，导致所有后续规则被忽略”不能完整解释现象。原输入共有181条规则缺少组成转向的有效路段，这些保留为数据质量问题，不擅自修改源案例。

## 转向输出的独立质量问题

`TVolNodecar.tsd`基准有920条带非GEOM端点的记录，流量为零；清空禁转后数量1011且部分异常编号改变。多数未限制路口的表格流量为零，而相应路段小汽车流量可以非零。应核实该表是否只覆盖特定节点、端点编号如何恢复、以及如何取得完整可信的转向/路径输出。

进一步覆盖审计确认：基准11,656个无禁转节点中的98,179个有效拓扑条目全部为零，而359个已有禁转节点中357个报告正值。全新节点对照会改变大量路段数组，与原有节点追加单条规则完全不变的结果不同。应优先核实节点转换、具体禁转应用及转向表重建之间的关系，详细证据见[诊断记录](禁转联动诊断.md)。

目标5990节点的进口和出口汇总与相邻`VolLinkCar.tsd`在显示舍入误差内一致，但原被限制的转向仍为正。这个局部一致性不证明全表或全部OD路径正确。

## 复现与证据

```powershell
python scripts/check_turn_response.py 智能体实验/jobs/20260908_040515_6a3455 S2_turn
python scripts/verify_turn_probe.py 智能体实验/probes/20260908_043338_multipath_tmp_turn
python scripts/probe_without_turn_rules.py --turn 6669 4994 4995
```

第一条检查预期返回1，准确捕获新增禁转响应未通过；第二条核验实验记录，但`turn_effective`仍为false。第三条会在新副本中真实重跑，不要与正在执行的模型争用同一运行环境。完整源输入、参数差异、模块stdout/stderr、运行时间与新生成输出均在对应实验目录。

进一步定位应优先明确：ManageNM是否还依赖其他未更新的中间文件；现有禁转节点上增加规则的处理过程；转向表的覆盖范围与有效编号；可用于验证禁转实际路径的官方输出。项目不会因进程成功退出就推荐这些未验证禁转。

当前进一步定位到默认程序构图中的局部禁转列表初始化为空，查找之前未见填入已读规则的步骤；带版本摘要、虚拟地址与指令的材料见[只读定位证据](诊断证据/禁转局部列表反汇编.txt)。请核实构图时是否遗漏从节点规则集合复制禁转对。另尝试同包Vehicle1程序时因缺少Mparam635参数文件失败，未将Mparam631直接改名代替。两者具体观察及未确认部分见[诊断记录](禁转联动诊断.md)。

另新增与ManageN无关的路段禁行对照：`20260908_060332_oneway`只把5991→5990的ManageR1四类机动车码0改2。缓存完整保留码2，五个车型Ljt文件本次新生成且只有该方向由474.67改为9,999,999,999，但目标小汽车、出租车、摩托车流量与四类完整路段数组均不变。请核实默认M6AssignVehicle实际使用的车型阻抗与M6TimeLinkManage输出的连接。配对输入和14调用、缓存格式与手册差异、图约束均见[单向组织验证](单向组织验证.md)。这只是本地追加材料，未对外发送。

后续只读核对Vehicle1的635读取器后，按七个整数与一个浮点数的实际顺序补齐参数，在新配对中单向禁行已响应，见[参数依据](诊断证据/Vehicle1参数与阻抗读取.md)与[配对结果](单向分配适配.md)。这不修改默认分配程序，也没有解决其新增禁转问题。Vehicle1保留的机动车TVolNode表为旧文件，不能用它核验禁转或跨程序推断根因。
