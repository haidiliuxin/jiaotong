# 双需求实测与跨需求量词 v7

## 真实运行与独立复核

自然语言问题明确给出需求系数 0.9 和 1.0、两需求各自新基准、同一停车措施的真实配对、最多四个场景。RC5 解压副本实际完成两基准＋同一三方向停车2级的两需求治理共四场景／28 个顶层原生模块；3 次模型请求、38,407 tokens。需求 1.0 的核心耗时下降 12.4943%，邻区耗时增加 0.4942%、毛新增过饱和 2.594 km，另一候选子区也超限；需求 0.9 的核心耗时下降 16.9928%，邻区耗时下降 0.1798%、毛新增过饱和 **0 km**，但另一候选子区耗时仍超限。实际推荐为保留基准。两需求小汽车 OD 输入和输出均逐项配对，包体运行后完整性检查通过。

原调度标记 `completed`，原 v6 工具核验也通过；独立语义复核为 **`needs_review`**。模型最终摘要说两需求都因“邻区新增过饱和超门槛”被拒，与 0.9 的 0 km 相反；H2 解释也把两需求都说成未过邻区门槛。正确结论是两需求都不具备推荐资格，但**各自失败条件不同**。原调度、状态和报告保持原字节，不追改 v6 通过记录。详见[独立复核](validation/20260930_demand_rc5_review.json)和[额度增量](validation/20260930_demand_rc5_budget_delta.json)。项目留存保守累计为 100 次请求、879,184 已知 tokens。

## 已实现的后续修正

新任务使用 `measured-conclusion-v7`。公开模型句子若对所有需求声称某项邻区代价都超限，校验器只在同一任务、同一措施编号、每个指定需求都有完整实测时，逐需求对照冻结门槛；有反例则拒绝并给出有界修正反馈。“均未同时满足”与“均未通过”都按明确的失败声称核查。不同措施编号或未配齐的格网保持未判，不猜测事实。模型提示要求逐需求列明具体违规项。旧 v6 记录仍按原协议回放；独立只读展示会把上述 RC5 原件标为 `needs_review`，不修改原件。当前源码复评 RC5 的旧协议核验仍通过，v7 影子复核检出 `summary` 与 `hypothesis_updates:H2` 两处冲突。625 项 Python 检查通过。

在封存的 RC5 实测输入上进行了两次**模型单独**调用，没有追加原生场景。首次 17,149 tokens，被 v7 拒绝：模型把原生次数用尽写成笼统的“预算已用尽”；最新检查还在 H2 发现 0.9 需求下的邻区门槛被误写成失败。随后按 `final-review-correction-v1` 传入这两项校验反馈，一次有界修正消耗 18,218 tokens；回复准确区分 1.0 的邻区超限与 0.9 的 area_2 超限，也明确模型额度尚余 3 次。修正回复通过 v7 与修正协议复核；首次拒绝仍保留，不能把这两次回复冒充新的仿真任务或把 RC5 原调度改成通过。原调度 SHA256 复核保持不变。见[两次探针复核](validation/20260930_demand_v7_model_probe_review.json)和[额度增量](validation/20260930_demand_v7_probe_budget_delta.json)。项目留存保守累计 **102 次请求、914,551 已知 tokens**，非完整账户账单。

源码提交 `16a6dae3` 的 RC6 便携 ZIP 已构建，包含 v7 修正。16,162 个不可变文件的清单、同机异目录环境与编译检查均通过；使用解压包内 Python 只读复核上述首次回复检出两项问题、修正回复无检出冲突，且对 RC5 原任务按 v6 协议核验通过。详情见[RC6 离线核验](validation/20260930_demand_v7_rc6_offline_validation.json)。

## 待验证

v7 已获上述限定的真实模型回复验证，尚未经过由 v7 运行时发起的完整模型加原生闭环；RC5 的真实仿真不能转记为 v7 完整验收。RC6 同机隔离也不是物理异机验收。文字检查只识别有界明确句式，不是通用语义证明；不同措施编号时保持未判。这个停车2级方案在两个离散需求点都不合格，不能因此断定其他位置、等级或连续需求范围均无效。物理异机、联合治理与完整最终交付仍待完成。
