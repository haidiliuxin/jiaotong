## 三 按优先级交接的工作

### P0 统一启动环境并完成真实复现

问题：本机禁转任务因缺少MinGW gcc无法通过依赖检查。测试本地HTTP访问受到系统代理环境影响。程序启动、依赖检查、历史档案核验与真实仿真成功属于不同层次，当前材料容易混淆。

建议工作：

- 提供统一启动脚本，定位Python 3.12并检查LFS实际文件、模型程序、适配器要求的编译器目标、端口和输出目录。
- 为本地请求设置进程级代理绕过，避免修改用户全局网络设置。
- 配置与适配器兼容的MinGW gcc，并在启动前显示清晰的缺项及解决步骤。
- 在本机运行四场景快速入门，保留本次新任务的日志、输出和独立核验；禁转若作为主要演示，应另验证对应完整流程。
- 在另一台电脑按相同说明真实运行，记录代码版本、依赖、输入摘要、运行时间和结果差异。软件授权须通过原软件正常检查。

验收标准：普通用户按说明可启动；停车快速入门完成并核验通过；宣称可运行的禁转或单向任务通过相应依赖与真实运行验证；另一台电脑留下可追溯的重跑记录。清楚区分测试通过、依赖通过、历史核验和真实重跑。

相关文件：`docs/智能体操作说明.md`、`traffic_agent/preflight.py`、`traffic_agent/runner.py`、`tests/test_web.py`、`examples/parking_quickstart.json`、`examples/turn_access_grid.json`。

### P1 补足治理措施和参数依据

问题：停车3级改2级或1级是离散模型参数，现实治理含义、停车需求承接与实施条件不够充分。候选筛选门槛和评价约束主要为预设实验假设，缺少系统的依据及敏感性说明。

建议工作：

- 编制“实际治理措施—模型字段—参数值—来源—适用条件”对应表，核对软件手册中的类别定义。
- 说明取消或规范路侧停车、限时管理等措施与模型情景的关系；无法验证的现实效果明确列为假设。
- 补充停车需求转移、绕行、步行距离和实施成本的讨论；没有数据时不编造数值。
- 解释候选门槛及邻区0.5%、全网0.1%、新增邻区过饱和0.1km等阈值的设定理由，并补充敏感性实验。

验收标准：每个关键参数能追溯到手册、数据或明确的实验假设；不得把停车类别差解释为线性容量变化，不得把预设阈值称为工程规范。

相关文件：`traffic_agent/data.py`中的`diagnose`、`traffic_agent/task.py`、`traffic_agent/knowledge.json`、`成果/参赛研究报告.md`。

### P1 避免微小收益驱动复杂方案推荐

问题：`recommend`首先按全网路段行驶时间排序，措施数量等因素在后。历史禁转结果中，S3组合相对S2单独禁转的全网耗时优势仅约0.058—0.102 pcu·h，邻区反而略差，不能据此宣称组合有明显工程优势。

建议工作：

- 设计最小有意义改善幅度，依据模型精度、数值稳定性与敏感性确定，实验前固定。
- 差异低于容差时，优先措施少、实施简单的方案；措施复杂度或成本须有明确可解释定义。
- 报告候选差异、选择依据，以及何时判定近似等效。
- 新旧规则分版本比较；不得修改历史推荐、原始结果或日志来适配新结论。

验收标准：微小收益不会无条件压倒措施复杂度；有临界值、近似等效、无合格候选等有意义测试；新规则使用独立结果记录，并说明结论变化。

相关文件：`traffic_agent/agent.py`中的`recommend`、`docs/禁转完整组合结果.md`、`智能体实验/jobs/20260908_100153_bb7198/`。

### P1 完善不利指标与取舍解释

问题：停车主实验核心速度约12.07→26.85 km/h，但核心过饱和里程没有减少，全网过饱和里程增加约0.584km。禁转组合在高需求下全网过饱和净增约0.8604km。原约束主要限制邻区新增过饱和，不能把通过约束等同于全面改善。

建议工作：

- 保留并突出不利指标，展示核心、邻区、全网的收益与代价。
- 评估是否引入全网新增过饱和、重点道路恶化或绕行代价的警示及约束。
- 若更改筛选条件，应预先固定并重新评估，不追溯性改变原实验的通过标准。
- 可提供多个可行方案及取舍，避免只显示单一推荐和绿色通过标签。

验收标准：用户能看懂方案改善哪里、恶化哪里、为何仍推荐或拒绝；路段Σ(qL/v)不得称为包含全部节点延误的全系统旅行时间；“通过约束”和“全部指标改善”明确区分。

相关文件：`traffic_agent/agent.py`中的`compare`、`traffic_agent/report.py`、网页静态文件、`成果/参赛研究报告.md`。

### P2 扩大迁移与敏感性证据

问题：环洲路迁移验证有效，但仍在同一数据库内，不能支撑跨城市、跨平台或普遍适用的结论。同预算对照主要针对一个冻结区域和三个需求点。

建议工作：

- 预先选择若干道路条件不同的区域，固定规则、候选预算和评价口径。
- 统一报告成功、回退、无候选及失败情况，不按实验结果挑选展示区域。
- 补充邻区范围、阈值和治理强度敏感性；条件允许时增加另一套兼容数据。
- 反馈策略对照可增加更有竞争力的固定策略；保持候选预算公平。

验收标准：有实验前的选区和协议记录；各需求独立匹配基准；迁移范围表述与证据一致；确定性复跑不得当作独立统计样本或统计显著性证据。

相关文件：`docs/区域迁移验证.md`、`docs/等预算实验协议.md`、`scripts/benchmark_feedback.py`、`scripts/verify_benchmark.py`。

### P2 统一正式报告与演示版本

问题：研究报告和部分验收材料仍写57项测试，当前为60项；现有录像早于新版地图。Markdown报告含相对图片链接及Mermaid，直接交付可能影响评审阅读。

建议工作：

- 按评分标准组织正式报告，提供每项要求的证据入口；注明提交版本和测试环境。
- 以停车反馈为主线、禁转为扩展、单向失败为反例，突出智能体如何根据结果改变决定。
- 更新视频覆盖新版地图、真实启动、反馈与结果；剪去等待时明确标注，保留同一任务ID。
- 将报告导出为比赛接受的正式格式，嵌入图表并检查可读性；提交说明未明确的格式、时长和大小不要自行当作官方要求。
- 制作精简交付入口，区分必需运行数据与历史归档，降低评审下载和理解成本。

验收标准：报告、视频、代码、任务ID和数字一致；五类成果齐全且离线可读；图表具有指标口径、单位、研究范围和需求配对说明；视频中的结果能追溯到任务记录。

相关文件：`成果/参赛研究报告.md`、`docs/方案一交付验收.md`、`成果/演示/README.md`、`docs/地图可视化说明.md`。

## 五 接手顺序与成果清单

建议按P0、P1、P2依次推进，首先确保现场运行，再提升决策依据，最后完善展示。当前不优先扩充未验证场景或引入大模型。

接手后应交付：

1. 启动与环境检查脚本、依赖说明及本机真实运行记录。
2. 异机复现记录，或明确列出尚未完成的验证。
3. 治理措施与参数依据表。
4. 推荐容差和多指标取舍的设计、实现、测试及新旧规则对照。
5. 预先登记的迁移与敏感性实验及完整结果。
6. 版本一致的正式研究报告、操作说明、视频和提交目录。

所有历史实验原始输入、结果和日志须保留。新算法、新阈值和新实验单独记录，不回填旧证据；仿真结果仅代表赛事调整案例，不得表述为南京真实交通改善。
