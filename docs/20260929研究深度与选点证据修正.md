# 研究深度与选点证据修正

本阶段继续自然语言驱动的 TranStar 批次规划。一次用户问题明确要求“比较至少两个不同的停车治理方案”，需求系数 1，最多三场景且不复跑。旧规划可能把它拆成多组，或测出第一个可行方案就结束。现把“先找一个可用方案”“比较多个实际候选”“核对需求变化”分别冻结为结构化研究深度；模型仍选择治理位置、等级和试验顺序。

## 已实现

- `research-depth-v1` 从原问题保留有据可查的短句和显式最少比较数；停车任务卡保存 `comparison_policies`，完成门槛数的是**不同且已经完成**的停车措施，不把菜单备选或基准算进去。旧任务未追加字段，仍按旧协议回放。
- 初始规划预算按一个停车研究组可运行多个候选计算；三场景可以是一份新基准加两个同需求治理。无关的“不支持能力”分支不再出现在本轮模型权限中。初始方案的范围和需求变化要求先校验再调度。
- 后续决策继续引用所选候选、备选和最近一次实际反馈。仅在观测引用缺漏、公开提议完整且预算能留出后续实验与复核时，允许一次付费修正；动作和备选均冻结。修正失败即停止，原始失败、两次用量和冻结观测可审计。没有由程序替模型补选方案。
- 单研究组发送模型的视图省去与本组初始假设完全相同的总任务假设副本；本地冻结输入和审计摘要仍保留全量。实际负面证据、结论代价、候选菜单及执行门槛继续提供给模型。
- 页面显示明确的研究深度、已实测候选数与停止理由。

## 已离线验证

612 项 Python 测试通过，覆盖研究深度、预算、修正权限、冻结动作、审计、历史协议和模型输入去重。补丁前四组 Node 检查通过；本次选点证据修正只改 Python。只读重放第二次实测的失败提议：仅加入遗漏的 `area_1` 新基准引用后，同一提议通过现有动作与实测结论校验；这不代表该措施的后续仿真结果。原任务和失败原件未改写。

## 真实验证与失败证据

首次有界调用在 `study_depth_workspace_20260929_01` 消耗 1 请求、7,670 tokens，模型误以为要两个停车组并提出无关的 `transit` 分支，初始校验拒绝，未启动原生。修正规划权限后，第二次在 `study_depth_workspace_20260929_02` 用 1 请求生成单停车组、两候选的三场景计划；新基准和首个停车治理均真实完成，各 7 个顶层 TranStar 模块。

首个措施是环洲路三个有向路段停车 1 级：固定核心耗时下降 28.5206%，邻区毛新增过饱和 2.797 km，超过冻结的 0.1 km 门槛，`eligible=false`。模型依据负反馈转向另一区域的第二个候选；该决策因漏引备选区域的新基准观测被 `choice_basis` 拒绝，故**第二措施未运行，整体 `incomplete`，未形成合格推荐**。这次共 3 请求、38,480 tokens、2 个原生场景。新选点修正流程在这些原件上只做离线检查，尚无真实 API 触发证明。两次运行及原记录保留原状。

两次新增请求按服务 `response_id` 去重，共 4 次、46,150 tokens；项目留存累计 76 次、576,178 tokens，上限仍为 684 次、4,132,560 tokens。这只是可核对的项目记录，不是完整账户账单。详见[额度增量](validation/20260929_study_depth_api_budget_delta.json)。
