# 相同规则在环洲路的区域迁移验证

研究问题：停车智能体是否能够只改变道路约束，继续完成新基准、区域候选、实测反馈、约束取舍和复跑，而不为新区域手工调整规则？

选区依据在试验前确定：任务`20260908_051630_12acc1`新基准的默认停车候选排名中，第一条为已研究的七东线3244→3245，第二条为环洲路3118→3117，qL/v优先分数216.2573。此次选择排名第二的未研究道路；不按治理结果筛选展示区域，也不将不同核心区的绝对收益直接排名。

任务卡：[parking_transfer_huanzhou.json](../examples/parking_transfer_huanzhou.json)。仅设置`road_name=环洲路`，继续采用最多3条路段、原候选筛选和邻区0.5%／全网0.1%／邻区新增过饱和0.1km阈值。预算4次，包含基准复跑；不加入额外需求敏感性，不能声称该区域在需求变化下稳定。

任务[20260908_053733_fe5765](../智能体实验/jobs/20260908_053733_fe5765/report.md)已完成，4个真实场景、28次模块调用通过[独立核验](../智能体实验/jobs/20260908_053733_fe5765/verification.json)。固定核心为3118→3117、3116→3115、3115→3116，共3条2.146km；邻区41条，全网32,060条有效道路。基准复跑的4类数组各32,981项逐项一致。

首轮虽改善核心区，但邻区行驶时间超过0.5%阈值，新增过饱和里程也超过0.1km。智能体在第二轮运行前决定缩小范围，只将3118→3117改为2级，其余核心方向保留原3级；固定评价范围没有随治理缩小。第二轮牺牲部分局部收益后通过全部预设约束，因此最终选择`parking_2`。

核心过饱和里程始终2.146km，反馈方案全网过饱和里程仍增加0.631km，不能称拥堵消除或全网所有指标均改善。补充公交审计在561条可完整评价线路上未发现运行时间变化，另93条明确排除；不推广到完整公交乘客收益。

第二轮后规则仍提出增强到1级，但已使用基准和两个候选共3次，4次总预算的剩余1次必须留给基准复跑，因此没有执行该候选。该任务使用运行时已加载的旧版日志结构，只记录`will_execute=false`；新增代码会明确记录`execution_gate`和`execution_reason`，不回填原任务以冒充当时已经输出了这些字段。

本例证明原规则在另一个道路范围上可以真实完成识别外溢、缩小范围与复现，不证明在所有区域可迁移，也没有验证该区域额外需求或更强治理。
