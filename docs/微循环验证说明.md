# 微循环验证工具与实验协议

本文的`circulation-trial`描述旧默认分配控制器。新状态图接口已完成四车型五轮的三场景配对、120次原生调用及独立核验，三种正流量车型目标转移归零；尚未接入本文S1/S3与需求流程，普通能力门槛不变。新证据与边界见[禁转完整分配适配](禁转完整分配适配.md)。

新增带`turn`的显式任务卡现接入独立状态图完整组合控制器；不带`turn`的历史任务保持下述旧默认流程。新控制器验收协议、入口和13场景预算见[禁转完整组合实验协议](禁转完整组合实验协议.md)，尚未据此开放普通能力。

## 范围与入口

本适配器用既有南京案例验证单个禁转和停车组合，尚不包含道路单向化。默认停车智能体的七东线核心区没有在既定绕行上限内找到合格禁转，不能为了得到S2而跳过约束。微循环任务在公开候选规则内另选验证区域，评价范围在新基准之后冻结。

```powershell
python -m traffic_agent plan --task examples/circulation_trial.json
python -m traffic_agent circulation-trial --task examples/circulation_trial.json
```

`circulation-trial`是显式验证入口。普通`run`及网页是否开放，由`capabilities`当前状态决定。实际输出放在`智能体实验/jobs/<任务编号>`，不会覆盖原案例。示例预算5次：新基准、S1停车2级、S2单个禁转、S3组合、同输入基准复跑。默认阈值仍为邻区时间增幅0.5%、全网时间增幅0.1%、邻区新增过饱和有向里程0.1km。任何方案都可能被拒绝，组合不预设优于单项。

结构化任务的`road_name`和`links`仍为硬约束；自动选点在停车瓶颈qL/v排序前30条中寻找可验证转向，并记录更高优先级候选被拒绝的原因。当前只取一个瓶颈、一项禁转，不把`max_links`解释为任意多禁转求解器。`max_feedback`不控制这个2×2固定对照；根据结果撤回禁转、选择停车或保留基准属于候选筛选反馈。

## 输入适配依据

- `城市交通版说明书.pdf`第30页表2-11与管理附录：ManageN六列为节点、该节点禁转总数、序号、from、via、to。写入同时维护头部不同节点数量和组内数量、序号，保留未涉及行的原始字节与GB编码。
- 手册公交输入表及案例`BusNodeBus.txt`、`BusNodeBRT.txt`：每行线路编号、节点数、节点序列。核对声明数量和每段有向路段存在性，保护所有相邻三节点转向；闭环线路也保护跨首尾转向。原案例共654条常规公交线路、0条BRT。
- 管理附录`ManageR1.txt`：from、to后依次为bike、car等模式。小汽车字段0可通行，1/2/3禁行。拓扑检查使用这一完整小汽车字段；不误用只表达区域禁行的缓存字段。
- `ManageNM.dat`为总禁转数加三节点序列。每次仿真先删除副本中的该缓存和`TVolNodecar.tsd`，要求模型重新生成并记录时间戳。

## 为什么使用转向状态

单纯从进口节点走到出口节点，可能忽略进入交叉口的方向和已有禁转。图的状态设为一条有向路段`(前节点,当前节点)`；前往`(当前节点,后节点)`前检查三节点转向。对每项新增禁转，寻找从原进口路段状态到原出口路段状态的替代路径，并让全部新增禁转同时生效，避免两个绕行互相依赖被禁的转向。

替代路径不允许即时掉头，不经过虚拟小区连接线；新增行驶距离最多2km，且从进口末端到原出口末端的总距离不超过原出口路段长度的3倍。这些是预先设定的保守实验限制，不是交通工程实施规范。

每个被删除的状态转移都有替代路径，则可用替换法保持该图原有的边状态可达关系。结论只覆盖编码中的小汽车通行、转向规则；未覆盖车牌分组、时段限制、道路净宽、未录入标志和软件内部的其他路径裁剪。原案例中不能组成有效小汽车转向的旧规则保留并计数，不擅自修复源数据。

## 如何证明禁转实际进入仿真

图检查只证明输入候选满足约束。执行后还必须：

1. 七个真实TranStar模块退出成功，四类路段结果、禁转缓存及小汽车转向矩阵均为本次生成。
2. 全部ManageN规则与ManageNM三元组集合完全相等，含原有规则和新增规则。
3. 同需求基准中新禁转的`TVolNodecar.tsd`流量大于1，禁转后降至0.01以下；缺失条目或原本为0不算通过。
4. 指标重新从结果文件计算，并与固定范围、同需求基准比较。图检查、软件响应、指标约束中任一项失败，都拒绝推荐该禁转。

这不能替代全部OD路径审计或现实执法证据。原案例很多路口的转向矩阵为零而路段流量非零，故不据此声称完整的节点流量守恒验证。转向矩阵中确实存在非零条目，验证选点以这些条目为必要条件。

## 输出审查

`diagnosis.json`记录候选与拒绝原因；`state.json`中`turn_response`记录缓存、前后转向量和公交/绕行检查；`report.md`显示同条件四种方案及被拒绝原因。`scripts/verify_experiment.py`独立重读输入、输出、指标、转向响应和推荐约束，不只读取任务“完成”状态。

补充公交影响使用`python scripts/audit_bus_impact.py 智能体实验/jobs/<任务编号>`。它验证本次新生成的`SpdLinkBus.tsd`，沿固定线路汇总Σ(60L/v)，同时列出变慢、变快和不能完整汇总的线路。该指标不包含乘客数、候车或换乘，且是实验后补充审计，不回改本次预先设置的推荐规则。图保护和运行影响不能相互替代。

若指定需求系数0.9/1/1.1，控制器会给最终推荐追加成对敏感性，并要求足够预算；这不是S0/S1/S2/S3全部需求水平的完整组合试验。完整试验和更多区域迁移仍需额外设计与实测。

首轮禁转未响应后的算法对照、失败记录及OD阶段采样见[禁转联动诊断](禁转联动诊断.md)。目前换为最短路增量后仍未响应，原因尚未定位；不能将诊断实验写成问题已修复。

后续已有显式转移图的单轮原生正例：出口成本拆分、独立出发接入、逐节点流量检查及原生复跑通过。该证据覆盖一轮小汽车新增禁转，不替代本页要求的完整S0/S1/S2/S3与多车型验证；普通禁转入口仍未开放，见[状态图诊断](禁转状态图原生诊断.md)。
