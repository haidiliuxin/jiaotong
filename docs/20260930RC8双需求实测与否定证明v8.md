# RC8 双需求实测与否定证明 v8

## 原生执行与真实回复

源码 `61c3654d` 的 RC8 便携包通过 16,162 文件完整性及同机异目录检查。另一目录解压副本收到“长江村路停车拥堵……需求系数0.9和1.0下是否稳健”的自然语言问题。新版定位许可没有追问“该道路”；初始模型生成一组四场景计划：两需求各新基准，再在各需求下执行**同一**停车1级、三个有向路段的治理。四场景及 28 个顶层原生模块均实际完成；4 次模型请求共 54,074 已知 tokens（初始 6,893、选点 13,346、最终首次 16,411、唯一一次有界修正 17,424）。

需求 1.0 的核心耗时下降 23.3087%，邻区耗时下降 0.1821%，邻区毛新增过饱和 0 km；需求 0.9 的核心耗时下降 18.1156%，邻区耗时**增加 0.0280%**，邻区毛新增过饱和 0 km。两场景按冻结约束均 `eligible=true`；0.9 的小幅正代价仍须保留。只覆盖这两个离散需求点、这一个位置和等级，不证明连续需求区间、动态排队或全网最优。

## 总任务为什么仍未完成

首次最终回复将需求 1.0 的 `has_measured_cost` 错填为 true，实测为 false，工具正确拒绝。模型得到有界反馈后改对该字段，并在风险文字中写“批次分配不证明动态排队回堵或零风险”。旧 `measured-conclusion-v7` 把句中的“零风险”误当肯定声称，再次拒绝。原调度终态为 **`incomplete`**，不能因四场景完成、内部候选 `eligible` 或状态文件暂存候选推荐而补发整体验收通过。完整总任务核验器也正确拒绝出具通过证明；原调度和状态文件保持字节不变。

## 有界修正及验证边界

新任务使用 `measured-conclusion-v8`，只把“不证明／不确认／不断言零风险”等明确否定证明句与“已证明零风险”区分。旧 v7 的原拒绝继续按 v7 复现。用 RC8 **实际的有界修正回复**和封存观测，只读影子应用 v8，工具参数、实测结论和修正权限核验均通过；这不是一个新真实回复，也没有改写 RC8 的 `incomplete` 记录。大厅任务列表对未完成任务显示“已测场景数 · 整项未完成”，不再把内部候选编号直接呈现为最终推荐。627 项 Python、`dispatch.js` 的 Node 语法检查、RC5 旧协议只读核验通过。证据与预算见[RC8 独立记录](validation/20260930_rc8_two_demand_review.json)。

当前项目留存保守累计 **107 次请求、975,295 已知 tokens**，上限 684 次／4,132,560 tokens；这不是完整账户账单。v8 尚未获得独立完整模型＋原生任务的通过结果，最终便携与物理异机验收仍待完成。

源码 `180294c9` 的 RC9 便携候选已构建并通过同机异目录检查。包内代码只读复现 RC8 的旧 v7 拒绝、v8 对同一修正回复的通过，以及 RC5 原 v6 任务的原协议核验；没有新增模型调用或原生场景。[RC9 离线记录](validation/20260930_rc9_v8_offline_validation.json)不替代新版完整真实验收。
