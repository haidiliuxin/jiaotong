# 停车备选研究范围与初始规划复核

## 问题与实现

原实现把“至少比较两个停车备选方案”的数量门槛与单向组的 S1/S2/S3 四格对照混算，因此只安排单向组合组也可能通过初始计划检查。界面又只渲染 `research-depth-v1`，新任务的研究深度卡片消失。

新任务使用 `research-depth-v3` 冻结 `candidate_domain=parking`，对明确的停车备选要求，只计停车研究内真正预留的不同候选。模型仍决定位置、方向、等级和试验顺序；程序只核对用户所要求的方案类别与场景数。`plan-compilation-v3` 在明确比较多个停车候选且模型提交结构完全相同的停车组时，将其合成一组同需求新基准与逐轮候选搜索，保留原提议序号，并按必需候选数重新核算原生和模型预算。不同道路、研究方法或控制组合继续保留独立组。v1/v2 研究深度按原版本回放。

页面现在显示 v1/v2/v3 冻结研究深度；若已启动停车研究，数量标成“本组已测齐”，不会把其他组或菜单中未执行的备选计入。

## 离线与真实初始规划

630 项 Python、4 组 Node 检查通过。合成边界覆盖：只提单向组不能满足“两项停车备选”、停车加单向时停车组仍须预留两项、重复停车组可编译为一组且保留两个原提议、旧 v2 深度解析仍按旧版本返回。RC5 完整任务使用当前代码 `verify_programme --no-write` 通过；RC8 原任务仍因记录的 `incomplete` 拒绝整体验收，原调度哈希不变。

使用同一句新自然语言做了两次**仅初始规划**真实服务探针。首次模型提议两个完全相同的自动停车组加一个单向组，旧编译器在仿真前拒绝；1 次请求、7,123 tokens，0 原生场景。随后在新编译逻辑下再次请求，模型直接提交一个停车组加一个单向组，任务卡 `ready`；停车组预留两个不同候选，最少 3 场景，单向组最少 4 场景，总共恰为用户的 7 场景上限；1 次请求、7,166 tokens，0 原生场景。这次真实回复没有实际触发重复组合并，该分支的验证仍为合成边界。第二次探针发生在将编译协议标签从 v2 升为 v3 之前，源码行为相同，最终标签本身未再次收费测试。

两次探针都没有调用 TranStar，也没有候选效果、停止决策或整体验收。当前项目留存保守累计为 **109 次请求、989,584 已知 tokens**，累计上限 684 次／4,132,560 tokens；不是完整账户账单。两次原件路径、SHA256 和账目见[独立记录](validation/20260930_parking_domain_initial_probes.json)。v8 完整模型加原生闭环、此新混合范围的执行质量与物理异机仍待验。

提交 `98fc4e0d` 的 [RC10 便携候选](../工作材料/便携构建/20260930_智能规划_v2_RC10.zip) 包含研究深度／编译 v3 与结论 v8。16,162 个不可变文件的清单、同机异目录环境和包内旧 RC5 原协议只读整体验证均通过；打包后没有新增模型请求或原生场景。压缩前曾误把 `.zip` 后缀传给构建器作目录名，已核对并将本次新建的完整 staging 目录移到正确目录名，再按构建器的 ZIP 参数压缩；独立解压与包完整性检验通过。详见[RC10 独立记录](validation/20260930_rc10_parking_domain_portable_offline.json)。
